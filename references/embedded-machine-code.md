## 命令性质

把 `置入代码` 当作编译期机器码嵌入指令，不要当作运行期执行源码或汇编文本的函数。

编译器在当前语句对应的代码位置原样写入所给字节。程序运行到该位置时，CPU 执行这些字节；此时不存在一次对 `置入代码` 支持库函数的运行期调用。由此得到以下约束：

- 命令本身无返回值；机器码如何向所在子程序交付结果属于目标 ABI，不是 `置入代码` 的返回值。
- 输入必须能在编译期确定。不要传入运行期变量，或声称修改变量即可动态改写已生成代码。
- 插入的是当前子程序中的指令片段，不是完整 PE、ELF、OBJ 或 COFF 文件。
- 编译器只复制字节，不解析其中的导入、符号、重定位、异常信息或数据段声明。
- 最终程序通常不因这一命令本身产生额外运行期支持库依赖，但工程中的其他命令仍可能需要支持库。

先判断是否真有必要使用机器码。能用已验证的核心命令、易模块、支持库、`.DLL命令` 或独立原生 DLL 完成时，优先使用这些可维护接口。

## 版本与输入形式

历史资料显示，`置入代码` 在易语言 4.12 之前属于特殊功能支持库，4.12 起移入核心支持库。处理旧工程时以工程声明和本机命令帮助为准，不要机械添加或删除 `.支持库 spec`。

保留原帮助资料的命令页给出的签名为：

```text
无返回值 置入代码 (代码数据)
```

其中 `代码数据` 为必需的通用型参数，文档列出两种编译期输入：

1. 字节集常量：最常见，字节按给定顺序直接写入代码段。
2. 二进制文件名文本：编译器读取文件中的原始字节。

不同 IDE 版本、Linux 版、普通编译、静态编译和第三方后端可能只支持其中一部分。使用文件名形式前查询当前命令帮助并做最小编译测试；不要仅根据网络示例推定支持。

字节集形式使用 0 到 255 的十进制字节。例如十六进制 `90 90` 应写成 `{ 144, 144 }`。`置入代码` 的参数是特殊的编译期输入，不要机械套用普通表达式规则，把它改成运行期的 `到字节集 (...)` 调用。

文件名形式应指向纯平面二进制文件，例如汇编器的 `bin` 输出，而不是 `.obj`、`.exe` 或带文件头的 `.com`。文件路径的相对基准随工具链而异；先用本地最小工程确认，并把该文件作为可复现的构建输入管理。

## 最小示例

用两个 x86 `NOP` 验证最安全：

```text
.子程序 机器码占位演示

置入代码 ({ 144, 144 })  ' 90 90: nop; nop
```

这个片段不改变寄存器、栈或控制流。编译后在反汇编中找到连续的 `90 90`，并确认它们位于目标子程序的预期语句位置。

某些版本支持从原始文件置入：

```text
置入代码 (读入文件 (“asm\helper.bin”))
```

只有本地命令帮助和编译测试确认文件名形式可用时才采用。生成源码时保留当前工程既有的引号风格。

`INT 3` 的 x86 字节是 `CC`，十进制为 204：

```text
置入代码 ({ 204 })  ' int 3
```

这会在代码路径被执行时触发断点异常，只能用于受控调试。不要把它留在交付构建中，也不要在无调试器的自动测试或生产环境运行。

## 编译位置与控制流

区分两种片段形态，并在设计时明确选择。

### 落回易语言代码

机器码完成少量操作后顺序执行后续易语言语句。此时：

- 不在片段中写 `ret`、`leave` 或跳到未知编译地址。
- 进入和退出时保持 `ESP` 相同。
- 不破坏编译器仍需使用的栈帧、寄存器、方向标志和运行库状态。
- 让编译器生成的 `返回 (...)` 和子程序尾声负责返回。

这是局部内嵌代码的优先形态，控制流风险较低。

### 从机器码直接返回

机器码自己恢复栈帧、放置返回值并执行 `ret`。此时它接管了后续控制流，源代码中位于其后的易语言语句在该路径上不会执行。

只有在反汇编确认当前编译器的函数入口、参数布局、隐藏参数、返回约定和清栈责任后才可使用。社区中常见的 `leave; ret N` 字节串不是通用模板；`N`、返回寄存器和尾声会随签名与编译后端变化。

不要在片段中提前返回后，又依赖后续 `返回 (...)` 修复结果或栈。源码层看似存在的兜底语句无法修复已经错误执行的机器级返回。

## 经典 Win32 x86 栈帧

经典 32 位编译结果中常见以下子程序框架：

```asm
push ebp
mov  ebp, esp
; 局部变量和保存寄存器
...
mov  esp, ebp
pop  ebp
ret  N
```

在这一特定框架下，返回地址通常位于 `[ebp+4]`，第一个 4 字节参数槽位通常位于 `[ebp+8]`，后续槽位常见 `[ebp+0Ch]`、`[ebp+10h]`。整数或地址型结果常经 `EAX` 返回。

这些只是需要用当前产物验证的常见观察，不是语言级保证：

- 字节型、短整数型在调用栈上可能仍占 4 字节槽位。
- `参考`、`数组`、`文本型`、`字节集`、`通用型` 和自定义类型可能传递地址、描述符或多级间接地址。
- 大对象、文本、字节集、64 位整数、浮点和对象返回可能有隐藏参数或不同返回位置。
- 优化可能省略 `EBP` 栈帧、重排局部变量、内联代码或改变寄存器分配。
- 普通编译、静态编译、黑月和其他第三方后端的入口/尾声不得互相套用。

需要访问参数时，先编写一个不含机器码、但签名完全相同的基线子程序，编译并反汇编其调用点和函数体。再从证据推导偏移、间接层级和清栈方式。

机器码片段处在现有函数内部，并不是独立 ABI 调用。至少遵守以下规则：

- 始终保持 `ESP` 平衡；每个 `push` 都要有匹配的恢复路径。
- 不改写 `EBP`，除非片段明确接管并正确恢复整个函数尾声。
- 按目标 ABI 保存 `EBX`、`ESI`、`EDI` 等非易失寄存器；对不确定的编译器活跃寄存器也应保存或从反汇编证明可覆盖。
- 使用字符串指令并设置过方向标志时，在退出前恢复 ABI 要求的 `DF=0`。
- 调用外部函数前满足其栈对齐、参数顺序、调用约定和寄存器保存要求。
- 不让 x87/SSE 控制状态、异常状态或栈深度在返回时失衡。

## 生成机器码

保留可读汇编源码作为事实来源，不要把一长串十进制数字当作唯一源代码。

推荐流程：

1. 固定目标架构、汇编语法和输出格式，例如 `x86-32`、NASM 语法、纯 `bin`。
2. 写无未解析外部符号的最小汇编片段。
3. 用汇编器输出原始字节，检查没有对象文件头、填充或意外段数据。
4. 用独立反汇编器按同一架构反汇编原始字节。
5. 把十六进制字节逐个转换为 0 到 255 的十进制数，或使用已确认的文件名形式。
6. 在易语言中置入后编译最终 EXE/DLL，再反汇编最终产物，而不是只检查中间 `.bin`。

示例转换：

```text
汇编器字节: 8B C0 90
十进制字节: 139, 192, 144
易语言形式: 置入代码 ({ 139, 192, 144 })
```

`8B C0` 是 `mov eax, eax`，`90` 是 `nop`。这个例子仅演示字节转换，不代表有实际业务价值。

如果使用生成工具，记录工具名称、版本、架构、源汇编和生成命令。对外部 `.bin` 保存哈希或在构建中重建它，避免文件被静默替换。

## 分支、调用与重定位

纯机器码复制不执行链接器工作。设计片段时区分以下情况：

- 片段内部的短跳转或相对跳转：汇编器在同一平面二进制内可计算时通常可用。
- 指向片段外部固定地址的跳转或调用：受最终布局和 ASLR 影响，不能硬编码网络样例中的地址。
- 对外部符号、导入函数、全局数据或其他段的引用：原始 `.bin` 中没有普通对象文件的重定位解析。
- `call rel32`：位移取决于调用指令末尾地址与目标地址之差；把在另一进程或另一构建中算出的 4 字节位移复制过来会跳错位置。

不要在平面片段中写 `.data`、未解析标签、`extern` 或依赖链接器导入表的 `invoke`，然后假定 `置入代码` 会补齐。调用 Win32 API 时优先写 `.DLL命令` 或使用工程中已验证的封装。确需从机器码调用时，运行期解析目标地址，并完整验证调用约定、位数、编码和错误处理。

为了跨构建稳定，优先写位置无关且只访问显式参数/缓冲区的片段。不要硬编码最终 EXE 中的绝对地址、易语言子程序地址、常量池地址或局部代码偏移。

## 易语言数据的内存表示

不要从旧机器码样例反推所有版本的内存布局。文本、字节集、数组、通用型、对象和自定义类型可能包含引用计数、长度、容量、类型标记、数据指针或内联数据，且普通编译与不同运行库可能不同。

特别注意：

- `参考` 参数通常增加至少一层间接访问，但确切层级要看调用点。
- 空文本、空字节集和共享常量可能使用特殊指针或只读存储。
- 修改长度、容量或引用计数字段可能破坏所有权，引发重复释放、越界或泄漏。
- 局部变量的 `[ebp-偏移]` 可能因新增变量、优化或编译版本而变化。
- 把文本/字节集内部地址保存到调用结束以后，可能形成悬空指针。

需要处理这类数据时，优先通过已验证的支持库 API 取得地址和长度；否则对当前运行库建立最小实验，分别检查空值、短值、长值、复制、传参考和释放路径，并把结论限制在该版本与编译模式。

## 编译后端与调试模式

机器码与生成它的目标架构绑定。x86 字节不能直接用于 x64、ARM 或其他架构。即使同为 x86，不同后端也可能改变栈帧、名称解析、运行库对象布局、清栈方式和优化策略。

不要用一个模式的结果替代另一个模式：

- IDE 调试运行可能使用与发布编译不同的包装、优化或加载路径。
- 普通编译与静态编译可能生成不同调用序列和运行库布局。
- 黑月是独立本机编译/链接后端；普通编译可用的偏移和尾声不能直接视为黑月保证。
- 第三方打包、加壳、LTO 或后处理可能改变代码地址和反汇编定位。

不能仅根据“调试运行”推断机器码一定执行或一定被忽略。用无副作用的 `NOP` 标记分别验证当前调试路径和最终发布产物；涉及 ABI 时，以最终目标模式的反汇编和运行测试为完成依据。

## 推荐工作流

1. 确认 IDE/编译器版本、核心库版本、目标系统、目标位数和编译后端。
2. 查询本机 `置入代码` 帮助，确认命令归属、参数形式和文件名输入支持。
3. 先搜索核心库、支持库、易模块、DLL API 和项目现有封装，确认机器码确有必要。
4. 固定易语言子程序签名，先编译不含机器码的基线并反汇编入口、调用点和尾声。
5. 编写带注释的汇编源码，明确每个参数、寄存器、栈槽、返回路径和副作用。
6. 生成并独立反汇编原始字节，逐字节核对。
7. 先用 `NOP` 确认置入位置，再替换为实际片段。
8. 编译最终目标模式，在最终 EXE/DLL 中定位字节并检查前后指令和所有控制流出口。
9. 在调试器中设置执行断点，记录进入/退出时 `ESP`、`EBP`、非易失寄存器和返回值。
10. 测试成功、失败、空值、边界长度、重复调用和多线程路径。

如果无法得到最终编译产物或无法反汇编，不要宣告机器码正确。可以提交可读汇编设计或待验证字节，但必须明确标注未验证的编译器、后端和 ABI 假设。

## 验证检查表

- [ ] 命令来源与当前编译器版本匹配。
- [ ] 输入是编译期常量字节或已确认支持的原始二进制文件名。
- [ ] 每个字节均能追溯到汇编源码和反汇编结果。
- [ ] 目标架构、位数和指令集扩展正确。
- [ ] 最终产物中的字节顺序与预期一致。
- [ ] 插入位置前后的反汇编控制流正确。
- [ ] 所有路径进入和退出时栈平衡。
- [ ] 参数偏移、间接层级和返回约定由当前产物验证。
- [ ] 非易失寄存器、方向标志和 x87/SSE 状态符合 ABI。
- [ ] 没有未处理的绝对地址、重定位、导入或跨段引用。
- [ ] 文本、字节集、数组和对象的生命周期没有被破坏。
- [ ] 调试、普通、静态或黑月等实际交付模式分别验证。
- [ ] 断点字节、临时跳转和测试填充未进入交付构建。

## 禁止做法

- 不从论坛复制十进制字节后仅凭“能编译”判断正确。
- 不把 `置入代码` 描述成运行期解释 C、汇编或易语言源码。
- 不用运行期变量冒充可动态修改的内嵌代码。
- 不硬编码另一版本中的 `[ebp+偏移]`、`ret N`、函数地址或 `call` 位移。
- 不把 `.obj`、`.exe`、任意下载文件或不受信任输入作为机器码置入。
- 不在未知 ABI 下修改文本、字节集、数组、对象内部字段或引用计数。
- 不在无调试器环境执行 `INT 3`，不把断点字节留在发布版本。
- 不用普通编译的成功结果替代静态编译、黑月或其他实际目标后端的验证。
